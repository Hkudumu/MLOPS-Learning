Good catch. In the current deployment YAML, we are NOT downloading the model automatically. You have to manually exec into the pod and run ollama pull every time the pod restarts. That's a problem.

The Problem with Manual Pull
Pod restarts → model is gone → manually exec again → pull again
Even with PVC, the model only persists if the pull was done after the PVC was mounted. But there's no automation.

3 Better Solutions

Solution 1 — Init Container (Recommended ✅)
Add an init container that pulls the model before the main container starts:
yaml
# ollama-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ollama
  namespace: ollama
spec:
  replicas: 1
  selector:
    matchLabels:
      app: ollama
  template:
    metadata:
      labels:
        app: ollama
    spec:
      # ─── Init container pulls model ONCE before main starts ───
      initContainers:
        - name: pull-model
          image: ollama/ollama:latest
          command: ["/bin/sh", "-c"]
          args:
            - |
              # Start ollama server in background
              ollama serve &
              OLLAMA_PID=$!
              # Wait for server to be ready
              echo "Waiting for ollama to start..."
              until ollama list > /dev/null 2>&1; do
                sleep 2
              done
              # Check if model already exists (skip if already downloaded)
              if ollama list | grep -q "qwen2.5-coder:7b"; then
                echo "Model already exists, skipping download"
              else
                echo "Downloading qwen2.5-coder:7b..."
                ollama pull qwen2.5-coder:7b
                echo "Download complete!"
              fi
              # Stop background server
              kill $OLLAMA_PID
          volumeMounts:
            - name: ollama-storage
              mountPath: /root/.ollama       # same PVC as main container
      # ─── Main container (model already downloaded) ───
      containers:
        - name: ollama
          image: ollama/ollama:latest
          ports:
            - containerPort: 11434
          env:
            - name: OLLAMA_NUM_THREAD
              value: "4"
            - name: OLLAMA_MAX_LOADED_MODELS
              value: "1"
          resources:
            requests:
              memory: "10Gi"
              cpu: "3"
            limits:
              memory: "14Gi"
              cpu: "4"
          volumeMounts:
            - name: ollama-storage
              mountPath: /root/.ollama       # shares same PVC
      volumes:
        - name: ollama-storage
          persistentVolumeClaim:
            claimName: ollama-models-pvc
---
apiVersion: v1
kind: Service
metadata:
  name: ollama-service
  namespace: ollama
spec:
  selector:
    app: ollama
  ports:
    - port: 11434
      targetPort: 11434
  type: ClusterIP
How it works:
Pod starts
  → Init container runs first
      → Starts ollama server in background
      → Checks if model already in PVC
      → If not: pulls qwen2.5-coder:7b into PVC
      → Stops background server
  → Main ollama container starts
      → Model already in PVC, ready immediately ✅
On pod restart:
Init container runs → model already in PVC → skips download → fast start ✅

what is the difference between vllm and ollama

Great question. Here's a comprehensive comparison:

Core Difference in One Line
Ollama  = Easy local deployment, built for individuals/dev
vLLM    = High performance production server, built for scale

Side by Side Comparison
Feature	Ollama	vLLM
Primary Use	Local/dev deployment	Production serving
Setup Difficulty	Very easy (1 command)	Moderate (needs GPU)
GPU Required	No (CPU works)	Yes (strongly recommended)
Throughput	Low	Very High
Concurrency	Limited	Excellent
Memory Efficiency	Basic	Advanced (PagedAttention)
Supported Formats	GGUF (quantized)	SafeTensors, AWQ, GPTQ
Streaming	Yes	Yes
OpenAI Compatible API	Yes	Yes
Windows Support	Yes	No (Linux/GPU only)
Batching	No	Yes (continuous batching)
Multi-GPU	No	Yes (tensor parallel)
Architecture Difference
Ollama
Request → Single queue → Load model → Generate tokens → Response
         (one at a time, simple)
vLLM
Request 1 ─┐
Request 2 ─┤→ Continuous Batching → PagedAttention → Parallel output
Request 3 ─┘  (all requests processed together efficiently)

Key Technical Differences
1. Memory Management
Ollama:
- Loads full model into RAM/VRAM
- One request at a time
- Simple memory allocation
- Can run on CPU via GGUF quantization
vLLM:
- PagedAttention: splits KV cache into pages
- Like virtual memory in OS
- Multiple requests share GPU memory efficiently
- 2-4x more requests per GPU vs naive serving
2. Batching
Ollama — No batching:
User 1 request → process → respond
User 2 request →           process → respond  (waits)
User 3 request →                      process → respond (waits longer)
vLLM — Continuous batching:
User 1 request ─┐
User 2 request ─┼→ batched together → all respond faster
User 3 request ─┘
3. Model Format
Ollama:
Uses GGUF — quantized format (Q4, Q8 etc)
✅ Runs on CPU
✅ Small file size
⚠️  Slight quality loss from quantization
vLLM:
Uses original HuggingFace weights (BF16/FP16)
✅ Full quality, no quantization loss
✅ Also supports AWQ/GPTQ quantization

Step 1 — Add GPU Nodepool to AKS
Add a GPU node pool to your existing AKS cluster: GitHub
bash
# Add GPU nodepool (NC series recommended for LLM)
az aks nodepool add \
  --resource-group <your-rg> \
  --cluster-name <your-cluster> \
  --name gpupool \
  --node-count 1 \

  --node-osdisk-size 200 \

Step 2 — Install NVIDIA GPU Operator
Deploy the NVIDIA Kubernetes plugin driver as a DaemonSet on your GPU node to ensure proper utilization of GPU resources within your cluster. anthropic
bash
# Add helm repos
helm repo add nvidia https://helm.ngc.nvidia.com/nvidia
helm repo add nfd https://kubernetes-sigs.github.io/node-feature-discovery/charts
helm repo update
# Install Node Feature Discovery
helm install --wait \
  --create-namespace \
  -n gpu-operator \
  node-feature-discovery nfd/node-feature-discovery \
  --set-json master.config.extraLabelNs='["nvidia.com"]'
# Install GPU Operator
helm install --wait \
  gpu-operator \
  -n gpu-operator \
  nvidia/gpu-operator \
  --set nfd.enabled=false \
  --set driver.enabled=false
# Verify GPU is detected
kubectl get nodes -o json | \
  jq '.items[].status.allocatable | select(."nvidia.com/gpu")'

Create a HuggingFace account and generate a user access token with the necessary permissions — it will be used to download models into memory when the container starts. anthropic

Step 5 — Deploy vLLM
yaml
# vllm-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm
  namespace: vllm
spec:
  replicas: 1
  selector:
    matchLabels:
      app: vllm
  template:
    metadata:
      labels:
        app: vllm
    spec:
      nodeSelector:
        agentpool: gpupool             # target GPU nodepool
      # ── Init container: download model into PVC first ──
      initContainers:
        - name: download-model
          image: python:3.11-slim
          command: ["/bin/sh", "-c"]
          args:
            - |
              pip install huggingface_hub -q
              python3 -c "
              from huggingface_hub import snapshot_download
              import os
              token = os.environ['HF_TOKEN']
              # Skip if already downloaded
              if not os.path.exists('/models/qwen2.5-coder-7b/config.json'):
                  print('Downloading model...')
                  snapshot_download(
                      repo_id='Qwen/Qwen2.5-Coder-7B-Instruct',
                      local_dir='/models/qwen2.5-coder-7b',
                      token=token
                  )
                  print('Download complete!')
              else:
                  print('Model already exists, skipping...')
              "
          env:
            - name: HF_TOKEN
              valueFrom:
                secretKeyRef:
                  name: hf-secret
                  key: token
          volumeMounts:
            - name: model-storage
              mountPath: /models
      # ── Main vLLM container ──
      containers:
        - name: vllm
          image: vllm/vllm-openai:latest
          command: ["python3", "-m", "vllm.entrypoints.openai.api_server"]
          args:
            - "--model=/models/qwen2.5-coder-7b"   # local path from PVC
            - "--host=0.0.0.0"
            - "--port=8000"
            - "--max-model-len=8192"
            - "--tensor-parallel-size=1"            # 1 GPU
            - "--gpu-memory-utilization=0.90"       # use 90% of VRAM
            - "--enable-prefix-caching"             # enable KV cache
          env:
            - name: HF_TOKEN
              valueFrom:
                secretKeyRef:
                  name: hf-secret
                  key: token
          ports:
            - containerPort: 8000
          resources:
            limits:
              nvidia.com/gpu: "1"                   # request 1 GPU
              memory: "20Gi"
              cpu: "4"
            requests:
              nvidia.com/gpu: "1"
              memory: "16Gi"
              cpu: "2"
          volumeMounts:
            - name: model-storage
              mountPath: /models
          # ── Health checks ──
          readinessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 60    # wait for model to load
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 120
            periodSeconds: 30
      volumes:
        - name: model-storage
          persistentVolumeClaim:
            claimName: vllm-model-pvc
---
apiVersion: v1
kind: Service
metadata:
  name: vllm-service
  namespace: vllm
spec:
  selector:
    app: vllm
  ports:
    - port: 8000
      targetPort: 8000
  type: ClusterIP
